# Open source data warehouses

Surprisingly, there are a lot of **open source** data warehouses. These can act as the main building block of a data platform.

It is a great choice instead of using one of the big proprietary data platforms (Snowflake, DataBricks or Microsoft Fabric).

## Research methodology

My research started with going through a list generated by ChatGPT for the following prompt:

> Give me a list of all open source data warehouses

Needless to say the list was not perfect. It included table formats (Iceberg, Hudi, Delta Lake), outdated technologies (Hadoop and Impala) and archived projects (Greenplum).

But nonetheless, it was a great starting point.

In my research I excluded projects that are specific to:
- Timeseries data - [QuestDB](https://github.com/questdb/questdb)
- Real-time processing - [Apache Druid](https://github.com/apache/druid) and [Apache Pinot](https://github.com/apache/pinot)
- Query engines - [Trino](https://github.com/trinodb/trino) and [Presto](https://github.com/prestodb/presto)
- In process databases - [DuckDB](https://github.com/duckdb/duckdb)

I also came across this interesting wikipedia [OLAP server comparison article](https://en.wikipedia.org/wiki/Comparison_of_OLAP_servers).

## How to choose?

It is easy to get paralysed by analysis when so many options are available.

All the slop generated by LLMs or clickbait articles (written with the help of LLMs) doesn't help either.

Finally, [benchmark wars](https://en.wikipedia.org/wiki/Benchmark_(computing)#Purpose) are still going on and add to confusion ([example 1](https://clickhouse.com/blog/write-side-cost-performance-snowflake-clickhouse), [example 2](https://www.snowflake.com/en/blog/engineering/efficient-snowflake-ingestion-query-ready/)).

So how to choose the backbone of a data platform for years to come without spending months on deep architecture reviews of each project and PoCs?

I found the below things useful:

1. Use funding and project popularity (GitHub stars) as a proxy for quality. Think natural selection.
2. Read intro docs for each project.
   - Often these describe the target use case. And sometimes (if your lucky) they emphasise when **not** to use it e.g. [Apache Druid docs](https://druid.apache.org/docs/latest/design/#when-to-use-druid) emphasise that you should **not** use it when there are big joins between large tables or where latency is not a key requirement.
