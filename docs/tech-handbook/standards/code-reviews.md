# Code Reviews

Little things make a big difference.

## Separate chat/channel for PR review

Separate chat/channel for PRs streamlines the PR review process and makes it easier to track which PRs are still to be reviewed.

## PR etiquette

Before posting a PR, ensure you have got it to work locally. If it’s not working locally, it’s not ready to be reviewed.

Post the PRs in the dedicated chat. Utilise the following emojis 

- 👀 – to indicate that you are reviewing the PR.
- 💬 – to indicate that you have left comments in the PR.
- ✅ – to indicate that you have approved the PR.

In case the PR has comments:

- Only the author of the comment must resolve the comment. This helps the reviewer to keep track which comments have been addressed.
- Don’t squash commits until the review is over, it makes it hard to track which comments have been implemented.
- Try to make each commit in way that it implements only 1 comment. This speeds up the review, since it easier to see which comments were implemented.

If reviewer has an improvement suggestion, a general comment with a brief description and/or some pseudo-code is sufficient. The reviewer doesn’t have to implement the improvement. It is up to the author of the PR to code up the improvement (if it has merits).

In cases where the improvement is valid, but not necessary immediately, then the PR author is responsible for creating a ticket in the backlog.

On large/complicated PRs, if a reviewer has multiple questions, it’s **always** better to jump on a call and walkthrough the code/thinking.

If there is back and forth on a comment, it is better to have a call / in person chat instead.

**Comments must always be respectful and constructive. PR reviews must never be used to belittle anyone or show off.**

## Differing opinions / decision making

It’s expected, and healthy, for there to be different opinions and approaches when it comes to implementation.

These conversations must **always** be respectful and constructive. All voices must be heard, and pros and cons of all approaches looked at.

If a compromise cannot be reached within a short conversation (~10 mins), bring in another team member for another point of view. If a solution still can not be found, then the more senior person is responsible for making a decision.

There is nothing wrong with the "disagree and commit" approach.

## Dealing with stakeholder pressure

If a stakeholder puts a lot of pressure to release faster, skipping thorough PR Reviews, escalate this immediately to your manager. 

There must be an **exceptional** circumstance to release something when it is not fully done, which can only be communicated by your manager.

In my life I have faced such circumstance only once. The company was on the brink of a bankruptcy and the only bet to save it was to release a new product ASAP (start-up style). If you are curious, the product was released successfully and saved the company.

## Discipline

All of the above will not matter if the team doesn’t follow through with these behaviours. Practice what you preach!
